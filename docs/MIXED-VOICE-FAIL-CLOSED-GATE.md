# Mixed-script voice gate for the exact 18.3.1 stock port

Status: candidate test plan and pinned DEX seam, **not a patch** or Android verdict.
Inputs: stock beta arm64 SHA-256 `2672a08a0292a307b9f62cd0fa6f48f3bc2334a2f2d9daff7db9d54fc4a2a7e3` and signed v32 SHA-256 `ce0d7e6710711f972e24ece2e838a3f51aff5184aeaeb78590dc1b14f182bd64`. Static assertions: `tests/test_pinned_voice_seams.py` and `tests/test_pinned_layout_pair_voice.py`.

## What the bytes show

V32 `classes.dex` `GboardRamblerScriptFix.processInternal(String,Locale,boolean)` calls `gateOpen`, then `containsBengali(input)` at instruction index 68. A true result immediately emits `skip:has-bengali` and returns the original input at index 73. `ensureDictionary`, `joinSplitPhrases`, and `SegmentLock.process` are later. `processVoice` calls `process(..., true)` with a voice enter/exit wrapper. This is a whole-input bypass, even for a candidate containing Bengali alongside Romanized Bangla. The independent `Lvrh.h` seam in v32 rewrites final nonempty `Lazdo.c` before dispatch, but neither seam proves the actual backend or editor commit. Ordinary typing and paste must remain unchanged.

C-1 is a separate hazard: v32 `LayoutPair.adjust` promotes the English layout to multilingual when its toggle is on and **any** bn-Latn subtype is enabled. The helper reads enabled IME subtype lists, not the selected subtype; its English check is an `en` prefix. EN-BN and ordinary English(US) can therefore be indistinguishable. Fail closed to English rather than changing ordinary English behavior until selected-subtype identity is proven on a device. Do not change typing layouts to fix voice.

## Consent-safe probe design and identity gate (source plan, not implemented)

Pinned v32 `classes3.dex` `Lvrh.h(Lazdg;)V` reads `Lazdg.b` final `Lazdo.c`, passes it to `ScriptFix.processVoice`, then writes the result into **that same** `Lazdo.c` before scheduling `Lvul`. A single guarded, diagnostic-only observer immediately before the `processVoice` invoke can see the *pre-transform final candidate*. A second observer after the `iput-object` can see the post-transform candidate. This **does not establish raw ASR**: earlier formatting, alternate candidate pruning, or backend behavior may precede `Lvrh.h`. Raw recognizer output needs its own independently identified producer-side boundary and owner descriptor. If that cannot be found and verified, mark raw ASR `UNOBSERVED` and do not claim an end-to-end engine diagnosis. The stock `Lvrh.h` has no conversion hook; a diagnostic stock build would have new bytes and must be identified separately from the uninstrumented stock control.

Only a physical, consented run with synthesized benign fixture audio may enable the diagnostic observers. The default release build must have no active observer and no retained candidate text. At the probe: derive in memory a fixture ID, event sequence, final flag, UTF-16 length, Unicode-script counts and a keyed digest of candidate bytes using an ephemeral per-run key; write only that limited metadata to a protected per-run trace, never logcat, analytics, crash reporting, public CI artifacts or a network endpoint. To link editor output without exposing text, compute its digest with the same ephemeral key. Delete the key and trace after the controlled comparison. Do not log or upload the owner's private dictation; if consent, matched fixture or provenance cannot be established, disable observers. Even a digest of a small vocabulary may leak if the key is retained, so key handling and access need review. Capture request locale, subtype and engine IDs in minimally identifying form; avoid account data. A diagnostic probe may perturb timing and call paths, so compare stock/v32 uninstrumented controls for selected backend, request header, candidate counts/order and commit behavior before treating the probe as representative.

Before **any** test run or review of an alleged candidate, record SHA-256 of the complete APK, size, package/version/certificate, parent stock APK hash, exact patch commit, observer revision and artifact path, then independently re-hash the same bytes at test install and evidence export. Also pin the test harness APK hash and fixture audio hash. There is **no new integrated candidate APK or hash today**; This documentation revision is not an APK. Do not substitute the signed v32 hash, staging shell hash or a prospective hash for the new candidate. Backend-preserving behavior remains a hypothesis until a physical controlled trace confirms it.

### Producer-side trace leads, not raw-ASR attribution

A narrow text-write scan of v32 `classes3.dex` smali found `Lazdo.c` writes in `Lkfo.d(Lkfb;)V`, `Lvxr.a(Lazkn;)V` (two writes), `Lkfv.d()V`, `Lqra`'s result-building path, and `Lvrh.h` (the conversion itself). These builders do not have a common proven recognizer origin. For example, `Lkfo.d` copies `Lkfb.a` into both a `Lazdn` string and a `Lazdo.c`; `Lvxr.a` builds a `Lazdg` with candidate text from a list. Neither proves that its input is the raw recognizer's output in the owner's selected backend. An instrumentation harness must map the live callback owner to the configured backend and fixture sequence, verify the producer's incoming text is pre-formatter/normalizer, and then align it with the `Lvrh.h` pre/post and editor events. If multiple producers are active, instrument each relevant one, not a convenient unexercised owner. No emitted payload or backend decision is claimed from this static scan.
