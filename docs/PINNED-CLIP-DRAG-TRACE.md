# Pinned clip reorder work plan, not a working drag build

Reference v32 signed APK SHA-256 `ce0d7e6710711f972e24ece2e838a3f51aff5184aeaeb78590dc1b14f182bd64`; exact stock SHA-256 `2672a08a0292a307b9f62cd0fa6f48f3bc2334a2f2d9daff7db9d54fc4a2a7e3`.

V32's pinned drag is not a one-method patch. `classes3.dex` `Lkut.p(Lra;I)V` attaches a listener via `GboardRamblerClipDrag.attach(Lkut,Lra,Object)`. The v32 `classes.dex` implementation initializes `GboardRamblerClipOrder` with the view context, and only attaches a listener for a `ClipAccess.isPinned` item. `ClipAccess` casts to `Lksw`, calls `Lksw.n()` to check pinned status and reads stable ID `Lksw.d:J`. The touch state machine posts `onArm` after Android's `ViewConfiguration.getLongPressTimeout()` and returns false on DOWN to preserve the stock listener. MOVE exceeding touch slop before arm removes the callback and returns false; MOVE below slop after arm still returns false; MOVE exceeding slop after arm calls `startDrag` and then `follow`, returning true. UP/CANCEL removes arm callback and resets state, returning whether a drag was active. `startDrag` dismisses the stock menu; `follow` handles active motion. This static branch sequence fits the owner's chosen hold-STILL versus hold-then-MOVE behavior but needs real UI validation. `follow` avoids unpinned targets, moves the item within `Lkut.o`, calls `Lkut.eH` to notify, and saves order. `finishDrag` saves again and animates translation home. `GboardRamblerClipSmooth` gates swaps. None of these are proven on-device just by DEX calls.

Persistence: `GboardRamblerClipOrder.save(List)` extracts only pinned `Lksw.d` IDs, caches a `long[]`, then writes the formatted IDs to SharedPreferences `rambler_clip_order` key `pinned_ids` when context exists. `load()` uses this cache/store. Existing host insert/rebuild hooks apply saved order in `Lkta.b(Object)` and `Lkut.E(SparseArray,List,int)`. Do not port drag alone: without both apply hooks, visual order could revert on refresh. Do not alter the underlying stored clip records or treat this as pin capacity. A later staging candidate must resolve all dependencies (`ClipAccess`, `ClipOrder`, `ClipDrag`, `ClipSmooth`, `Lkut.p`, `Lkta.b`, `Lkut.E`) and test unpinned/empty/rapid press/cancel/rotation, persistence after keyboard restart, normal tap and original stock long-press menu, and order after pin/unpin. The owner chose option A among the three proposed drag interactions: (a) hold then move starts drag while hold-still opens menu; (b) edit/select mode; (c) drag handle. This supports the hold-still/hold-then-move plan. v32's drag arm/motion state may match it, but still needs runtime negative controls for still hold, ordinary tap and cancel; selected UX is not a device pass.

The current unsigned picker+recents prototype SHA-256 `f2408b96889f429cec7127620a0aecd1b41069203c8202907c030a683bf12294` has **no drag behavior**. No signing, production update or device claim follows from this plan.
